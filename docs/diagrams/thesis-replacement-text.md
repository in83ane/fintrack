# ข้อความทดแทนสำหรับรายงาน FinTrack

ฉบับร่างอิงโค้ด ณ 13 ตุลาคม 2026 ใช้คัดลอกไปจัดเล่มในต้นฉบับแก้ไขได้ ไม่ใช่ผลวิจัยที่ยืนยัน production หรือผลทดลองกับผู้ใช้

## ชื่อเรื่องที่เสนอ

ภาษาไทย: การพัฒนาระบบติดตามพอร์ตการลงทุนและจัดการการเงินส่วนบุคคลเพื่อรองรับ Web App, PC App และ Mobile App

ภาษาอังกฤษ: Development of an Investment Portfolio Tracking and Personal Finance Management System for Web, Desktop, and Mobile Applications

ชื่อเรื่องนี้เป็นข้อเสนอ ต้องยืนยันกับอาจารย์ก่อนใช้ปกจริง ไม่เติมชื่อผู้จัดทำ สาขา อาจารย์ และปีการศึกษาโดยเดา

## บทคัดย่อภาษาไทยฉบับร่าง

โครงงานนี้มีวัตถุประสงค์เพื่อพัฒนาระบบ FinTrack สำหรับรวบรวมข้อมูลพอร์ตการลงทุนและการเงินส่วนบุคคลไว้ในระบบเดียว โดยมีเป้าหมายรองรับ Web App, PC App และ Mobile App ใช้ข้อมูลและกฎการเงินร่วมกัน ฟังก์ชันหลักประกอบด้วยการจัดการพอร์ตและบัญชีเงินสด การบันทึกรายการลงทุน การวางแผนซื้อแบบแบ่งไม้ การบันทึกรายรับรายจ่าย และการจัดสรรเงินตามเป้าหมาย รุ่นที่พัฒนาและตรวจสอบในรายงานนี้เป็น Responsive Web Application ด้วย Next.js, React และ TypeScript ร่วมกับ Supabase สำหรับบริการยืนยันตัวตนและฐานข้อมูล PostgreSQL ส่วน PC App และ Mobile App เป็นแผนพัฒนาต่อยอดพร้อมการทดสอบเฉพาะแพลตฟอร์ม

ระบบแสดงข้อมูลราคาจากผู้ให้บริการภายนอกและเครื่องมือกราฟ TradingView พร้อมแยกกำไรขาดทุนที่รับรู้แล้ว กำไรขาดทุนของหุ้นที่ยังถืออยู่ และผลรวม การแปลงมูลค่าเพื่อแสดงผลใช้เรท USD/THB ร่วมกัน โดยแยกจากเรทที่บันทึกกับรายการซื้อขาย การคำนวณ cost basis ในโมดูลเฉพาะใช้ค่าทศนิยมแบบแม่นยำและสามารถตรวจผลก่อนยืนยันการขายได้ ทั้งนี้ ระบบเป็นเครื่องมือบันทึกและติดตามข้อมูล ไม่ใช่ระบบส่งคำสั่งซื้อขายหลักทรัพย์จริง

ผลการพัฒนาและผลการทดสอบต้องรายงานแยกกัน โดยอ้างอิงกรณีทดสอบที่ดำเนินการจริง ข้อจำกัดที่ต้องประเมินเพิ่มเติมประกอบด้วยความสอดคล้องของข้อมูลเดิมที่ไม่ระบุสกุลเงิน การทดสอบสิทธิ์บนระบบที่ติดตั้งจริง ประสิทธิภาพภายใต้ภาระงาน และความพึงพอใจของผู้ใช้

คำสำคัญ: การติดตามพอร์ตการลงทุน, การเงินส่วนบุคคล, การแบ่งไม้ลงทุน, อัตราแลกเปลี่ยน, เว็บแอปพลิเคชัน

## 1.1 ความเป็นมา — เป้าหมายหลายแพลตฟอร์ม

โครงงานนี้มุ่งพัฒนา FinTrack เพื่อรองรับ Web App, PC App และ Mobile App โดยใช้ข้อมูลบัญชีและกฎการคำนวณทางการเงินร่วมกัน ระยะปัจจุบันพัฒนาเป็น Responsive Web Application สำหรับใช้งานผ่านเบราว์เซอร์บนคอมพิวเตอร์และอุปกรณ์เคลื่อนที่ ส่วนแอปติดตั้งบนคอมพิวเตอร์และมือถือเป็นระยะพัฒนาต่อยอดที่ต้องจัดทำตัวแอปและทดสอบเฉพาะแพลตฟอร์ม ระบบรวบรวมข้อมูลพอร์ตการลงทุน รายการซื้อขาย กระแสเงินสด และการจัดสรรเงินไว้ในระบบเดียว เพื่อช่วยลดขั้นตอนการรวบรวมข้อมูล ทั้งนี้ ประโยชน์ด้านระยะเวลาการใช้งานและความพึงพอใจต้องยืนยันด้วยการประเมินผู้ใช้เพิ่มเติม

## 1.2 วัตถุประสงค์

1. เพื่อพัฒนาระบบจัดการพอร์ตการลงทุนและการเงินส่วนบุคคลโดยมีเป้าหมายรองรับ Web App, PC App และ Mobile App ใช้บัญชีผู้ใช้และกฎการเงินร่วมกัน เริ่มจาก Web App และต่อยอดแอปติดตั้งในระยะถัดไป โดยแยกพอร์ตลงทุน บัญชีเงินสดของโบรกเกอร์ และเงินใน Bucket อย่างชัดเจน
2. เพื่อพัฒนาการวางแผนซื้อแบบหลายไม้ การตรวจสอบผลก่อนขาย และการแสดง Realized, Unrealized และ Total P&L พร้อมการแปลงมูลค่าแสดงผลด้วยเรท USD/THB ร่วมกัน
3. เพื่อตรวจสอบความถูกต้องของกรณีใช้งานที่กำหนดด้วยการทดสอบซอฟต์แวร์ และกำหนดแนวทางประเมินการใช้งานจริง โดยรายงานผลเฉพาะส่วนที่ดำเนินการและมีหลักฐานแล้ว

หากหลักสูตรกำหนดให้มีการประเมินผู้ใช้จริง ให้คงวัตถุประสงค์นั้นและดำเนินการเก็บข้อมูล ห้ามเปลี่ยนข้อความเป็นผลสำเร็จเพื่อหลีกเลี่ยงการประเมิน

## 1.3 ขอบเขตระบบ

ขอบเขตเป้าหมายครอบคลุม Web App, PC App และ Mobile App โดยแบ่งส่งมอบเป็นระยะ: รุ่นที่ตรวจมี Web App แบบ Responsive; ระยะถัดไปเป็นแอปติดตั้งบนคอมพิวเตอร์และมือถือ ซึ่งต้องพัฒนา platform adapter สำหรับ session, navigation, storage และการเชื่อมต่อเครือข่าย พร้อมทดสอบแยกแพลตฟอร์ม ไม่ถือว่าการเปิดเว็บบนมือถือเป็นหลักฐานการส่งมอบ Mobile App แล้ว ฟังก์ชันร่วมประกอบด้วยการจัดการพอร์ตและบัญชีเงินสด การบันทึกรายการลงทุน การวางแผน DCA การวิเคราะห์กราฟใน Terminal การจัดการ Bucket และกระแสเงินสด รวมถึงหน้าสรุปและประวัติ

การแสดงผลสกุลเงินที่ใช้เรทกลางในรุ่นนี้ครอบคลุม USD และ THB ขณะที่ชนิดข้อมูลบางส่วนรองรับชื่อ JPY และ EUR แต่ยังไม่ใช้เป็นหลักฐานว่าการแปลงด้วยเรทสดของสองสกุลนี้ทำงานครบถ้วน ข้อมูลราคาอัปเดตเป็นระยะตามการเรียก API และข้อจำกัดของผู้ให้บริการ ไม่รับรองว่าเป็นข้อมูลเรียลไทม์จากตลาดโดยไม่มีความล่าช้า

ระบบทำหน้าที่บันทึกและวิเคราะห์ข้อมูลการลงทุน ไม่ส่งคำสั่งซื้อขายจริงไปโบรกเกอร์ การรองรับแต่ละตลาดและชนิดสินทรัพย์ต้องพิจารณาจากข้อมูลของผู้ให้บริการและกรณีที่ผ่านการทดสอบ ไม่ใช้เพียงรายการตัวเลือกในฟอร์มเป็นหลักฐานว่ารองรับครบทุกกรณี

## 2.2.1 React และ Next.js

React ใช้สร้างส่วนติดต่อผู้ใช้แบบองค์ประกอบ ส่วน Next.js ใช้จัดการเส้นทางและการทำงานร่วมกันระหว่างฝั่ง browser กับ server โครงงานนี้มีทั้ง route handlers/server actions สำหรับบริการข้อมูล และหน้าจอหลายส่วนที่ประกาศใช้ client components การเลือก Next.js จึงไม่ได้หมายความว่าข้อมูลทางการเงินทุกส่วนถูก render ที่ server และไม่สามารถใช้แทนผลวัดความเร็วหรือ SEO ของระบบจริงได้

## 2.3.2 การกำหนดสิทธิ์ข้อมูลและขอบเขตพอร์ต

ระบบใช้ Supabase Auth และมีโครงสร้างข้อมูลที่อ้างถึงผู้ใช้และพอร์ต เช่น user_id และ portfolio_id ภายใน repository มีคำสั่งสำหรับกำหนดนโยบายการเข้าถึงระดับแถวและฟังก์ชันฐานข้อมูล การรับรองความปลอดภัยต้องตรวจการตั้งค่าที่ถูกใช้งานจริงและทดสอบการเข้าถึงข้ามผู้ใช้เพิ่มเติม ไม่สรุปว่าปลอดภัยเพียงเพราะเลือกใช้ Supabase หรือมี SQL policy อยู่ใน repository

## 2.4 การแสดงผลข้อมูลและเลขทศนิยม

ระบบใช้ Recharts ในการแสดงข้อมูลสรุป และใช้ TradingView embedded widgets ในส่วนกราฟตลาด โดยแยกการแสดงกราฟจากตรรกะที่คำนวณขึ้นภายในแอป โมดูล cost basis ใช้โครงสร้าง Decimal ที่คำนวณแบบ rational ด้วย BigInt และส่งค่าที่ขอบเขตข้อมูลเป็น decimal string เพื่อลดปัญหาจาก binary floating point อย่างไรก็ตาม โมดูล legacy บางส่วนยังใช้ number จึงไม่ควรกล่าวว่าทั้งระบบไม่มีการคำนวณแบบ floating point

## 3.2 สถาปัตยกรรมระบบ

ระบบแบ่งออกเป็นส่วนติดต่อผู้ใช้ใน browser ส่วนบริการของ Next.js ส่วน Supabase และผู้ให้บริการข้อมูลภายนอก AppContext จัดการสถานะร่วมและการเรียกดำเนินการทางการเงิน ขณะที่ Supabase SDK สามารถเรียก Data API และ RPC ได้โดยตรง ส่วน API และ server actions ของ Next.js ใช้สำหรับข้อมูลราคา กราฟ และ FX บางส่วน จึงไม่ใช่สถาปัตยกรรมที่ทุก request ต้องผ่าน custom backend endpoint เดียว

แทรกภาพจาก 01-system-architecture.mmd สำหรับระบบปัจจุบัน และ 01b-system-architecture-target.mmd สำหรับเป้าหมาย Web App / PC App / Mobile App โดยระบุใน caption ว่าส่วนใดเป็นแผนพัฒนา ไม่รวมสองสถานะเป็นผลสำเร็จเดียวกัน

## 3.3 ผู้ใช้และการใช้งาน

ผู้ใช้งานเลือกพอร์ต ค้นหาหุ้น และสลับระหว่าง Terminal กับ Trade Plan โดยส่ง symbol เดียวกัน การสร้าง draft ไม้ DCA ยังไม่ทำให้เกิดหุ้นที่ถืออยู่จนกว่าจะยืนยันบันทึกรายการซื้อ สำหรับการขาย ผู้ใช้เลือกไม้เองหรือแบ่งจำนวนขายตามสัดส่วนหุ้นที่เหลือ จากนั้นตรวจ preview และยืนยัน symbol ก่อนบันทึก

แทรกภาพจาก 05-use-cases.mmd และ 02-user-flow.mmd การใช้ flowchart จำลอง Use Case ต้องระบุให้ตรงกับ notation และข้อกำหนดของอาจารย์

## 3.4 แบบจำลองข้อมูลในโปรแกรม

แบบจำลองสำคัญได้แก่ BuyLot, SellTransaction, Position, LotAllocation และ Ledger จำนวนซื้อเดิมกับจำนวนที่เหลือมีความหมายต่างกัน โดยจำนวนที่เหลือเป็นผลจากการ replay รายการซื้อขาย ไม่ใช่การแทนที่ประวัติจำนวนซื้อเดิม LotAllocation ในที่นี้เป็นโครงสร้างข้อมูลในโมดูลคำนวณ ไม่ใช่ตารางฐานข้อมูลที่ปรากฏใน schema ที่แนบ

## 3.5 การออกแบบฐานข้อมูล

schema ที่ใช้เป็นเอกสารอ้างอิงประกอบด้วย 18 ตาราง public และอ้างถึง auth.users ผ่าน foreign key โดย profiles.id เป็นทั้ง primary key และ foreign key ทำให้ผู้ใช้หนึ่งรายมี profile ได้ไม่เกินหนึ่งแถว ส่วนตารางธุรกรรมแยกจากบัญชีเงินสดและ Bucket การออกแบบแผนภาพต้องคง nullability ของ foreign key ตาม schema ไม่สมมติว่าทุกรายการมี portfolio หรือ asset เสมอ

history_events ใน schema นี้จำกัด source_table เป็น trades จึงต้องแยกจากหน้า Ledger ที่แสดงข้อมูลหลายแหล่ง assets ไม่มีคอลัมน์ currency ใน schema ที่แนบ ส่วนความหมายของยอด legacy ต้องตรวจและยืนยันเป็นรายแหล่ง ไม่เดาจากชื่อหุ้น

ใช้ 04-er-full.mmd และ database-dictionary.md แบ่ง ER เป็นภาพย่อยเมื่อนำลงหน้ากระดาษ และเก็บฉบับเต็มไว้ภาคผนวก

## 3.6 ลำดับการทำงาน

การขายเรียก cost_basis_preview ก่อนเพื่อแสดง before/after และ fingerprint จากนั้นส่งคำขอยืนยันผ่าน cost_basis_sell และแจ้งให้สถานะร่วมโหลดใหม่ สำหรับรายรับรายจ่าย เส้นทาง AddCashflowModal เรียก AppContext ซึ่งเพิ่ม optimistic row ก่อนเรียก Supabase client หาก insert ล้มเหลวจะถอน optimistic row ออก ส่วนรายการที่เกี่ยวกับ Bucket อาจมีการ update balance และ insert activity เพิ่มเติม จึงไม่ควรอธิบายว่าเส้นทางนี้เป็น database transaction เดียวจนกว่าจะมีหลักฐานรองรับ

ใช้ 06a-sequence-sale.mmd และ 06d-sequence-cash-activity.mmd ส่วน shared FX และการนำทางใช้ 06b/06c

## 3.7 แผนการทดสอบ

| กลุ่ม | กรณีทดสอบ | หลักฐานที่ต้องเก็บ |
|---|---|---|

| Security | ผู้ใช้ A อ่าน/แก้ข้อมูล B ไม่ได้ | isolated test users, denied response และ policy version |
| Performance | เวลาโหลดและตอบสนองภายใต้เงื่อนไขที่กำหนด | device, network, dataset size, จำนวนรอบ, p50/p95 |
| Usability | ความสำเร็จของงานและความพึงพอใจ | จำนวนผู้เข้าร่วม วิธีเก็บข้อมูล แบบสอบถาม และผลจริง |

ตารางนี้เป็นแผน ไม่ใช่ผลการทดสอบผ่าน ห้ามใส่ค่า actual ที่ไม่ได้วัด

## 4.1 ผลการพัฒนาที่สรุปได้จากโค้ด

พบ implementation ของหน้าจอจัดการพอร์ต บัญชีเงินสด กระแสเงินสด Bucket และ Trade Plan รวมถึงการตรวจ preview ก่อนขายและการแสดง P&L แยกประเภท การแสดงเรท USD/THB ใช้ shared store เดียวกัน และหน้ารายละเอียดมีการเรียกข้อมูลตลาดตามรอบที่กำหนด ความถูกต้องต้องอ้างอิง test cases ที่ระบุ ไม่เหมารวมว่าทุกข้อมูลและทุกตลาดผ่านการตรวจแล้ว

โมดูลผู้ช่วยที่พบใช้การจับคำค้นและกฎจากข้อมูลในแอป จึงเรียกว่า rule-based assistant ในรายงานรุ่นนี้ การมี dependency สำหรับ AI ไม่ใช่หลักฐานว่าฟังก์ชันดังกล่าวเรียก LLM ส่วนหน้าสัญญาณเดิม /trade/[symbol] ถูกนำทางไป Terminal จึงไม่ควรใช้เป็นหลักฐานของหน้าเปิดใช้งานแยกในรุ่นปัจจุบัน

## 4.2 ผลการทดสอบ — โครงข้อความที่ไม่อ้างเกินหลักฐาน

ให้แยกผลทดสอบอัตโนมัติ ผลทดสอบ browser และผลประเมินผู้ใช้ โดยแต่ละผลระบุเวอร์ชันโค้ดหรือวันที่ environment คำสั่งทดสอบ จำนวนกรณี และข้อจำกัด การทดสอบ type checking ไม่ใช่ performance test และผลจาก mock ไม่ได้ยืนยันสิทธิ์หรือพฤติกรรมของฐานข้อมูล production

ชุดคำสั่งที่มีอยู่ให้ตรวจและเลือกใช้อย่างเหมาะสม เช่น scripts/test-fx.mjs, scripts/test-native-money.mjs, scripts/test-cost-basis-ledger.mjs และ scripts/test-shared-market-symbol.mjs ไม่ให้ระบุว่าผ่านจนกว่าจะรันและแนบผลของรุ่นที่ส่งรายงาน

## 4.3–4.4 การอภิปรายและข้อค้นพบ

การรวมข้อมูลพอร์ตและเงินสดไว้ในระบบเดียวมีความสอดคล้องกับแนวคิดการติดตามสถานะทางการเงินแบบรวมศูนย์ อย่างไรก็ตาม การพิสูจน์ว่าผู้ใช้ทำงานเร็วขึ้น ตัดสินใจลงทุนดีขึ้น หรือมีวินัยทางการเงินมากขึ้น ต้องอาศัยวิธีประเมินและข้อมูลเพิ่มเติม ไม่สามารถสรุปจากการมีฟังก์ชันหรือการอ้างงานวิจัยอื่นเพียงอย่างเดียว

ข้อค้นพบจากการพัฒนาคือจำเป็นต้องแยกยอดในสกุลเดิมจากมูลค่าที่แปลงเพื่อแสดงผล แยก draft จากรายการที่บันทึกแล้ว และแยกประวัติธุรกรรมจาก projection ของยอดปัจจุบัน ข้อจำกัดยังรวมถึงข้อมูล legacy, นิยาม metrics ที่ต่างกันระหว่างบางโมดูล และการยืนยันค่าตั้งด้านสิทธิ์บนระบบจริง

## 5.1 สรุปผล

โครงงานได้พัฒนาเว็บแอปพลิเคชันที่รวมการติดตามพอร์ตการลงทุน การบันทึกกระแสเงินสด และการจัดสรรเงินตามเป้าหมาย โดยมีส่วนวางแผนซื้อหลายไม้และตรวจสอบผลก่อนขาย การเลือกหุ้นร่วมกันระหว่าง Trade และ Terminal และการใช้เรทแสดงผล USD/THB ร่วมกันช่วยลดความแตกต่างของข้อมูลระหว่างหน้าจอ ทั้งนี้ ผลที่กล่าวเป็นผลด้าน implementation; ข้อสรุปด้านประสิทธิภาพ ความปลอดภัย และความพึงพอใจต้องอ้างอิงผลทดสอบที่ดำเนินการจริงแยกต่างหาก

## 5.2 ข้อเสนอแนะ

1. ตรวจและยืนยันสกุลของข้อมูล legacy ก่อน migration โดยไม่เดาและไม่เปลี่ยนประวัติย้อนหลังโดยไม่มีหลักฐาน
2. รวมเส้นทาง cashflow ที่ต้องเขียนหลายตารางให้อยู่ในขอบเขต transaction ที่ตรวจสอบได้ พร้อมกรณีทดสอบ failure
3. ทำให้นิยามและสูตร metrics ทุกหน้าเหมือนกัน และแทนค่า placeholder ใน analytics ด้วยข้อมูลที่เหมาะสม
4. ตรวจ RLS และ authorization บน deployment จริง พร้อมทดสอบการเข้าถึงข้ามผู้ใช้
5. เก็บผล performance และ usability ด้วยวิธีที่ทำซ้ำได้
6. พัฒนา PC App และ Mobile App เป็นระยะถัดไปของเป้าหมายหลายแพลตฟอร์ม โดยใช้บริการข้อมูลและกฎการเงินร่วมกับ Web App แต่แยกการจัดเก็บ session, deep link, navigation และการทดสอบเฉพาะแพลตฟอร์ม การรองรับสกุลเพิ่มเติมและ LLM assistant เป็นงานต่อยอดแยกกันจนกว่าจะมี implementation และผลทดสอบรองรับ

## เอกสารอ้างอิงและข้อมูลที่ยังต้องเติม

ตรวจชื่อเรื่อง ผู้แต่ง ปี วารสาร เล่ม หน้า DOI/URL ของงานวิจัยที่อ้างในบท 2 และ 4 จากต้นฉบับก่อนจัดบรรณานุกรม ไม่สร้างรายการอ้างอิงที่ยังไม่ยืนยัน ไม่แทนที่ข้อมูลนักศึกษา/อาจารย์หรือผลประเมินจริงด้วยข้อความสมมติ
